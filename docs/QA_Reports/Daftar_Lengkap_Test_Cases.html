LAMPIRAN: DAFTAR LENGKAP TEST CASES

Penjabaran detail dari 74 test case (assertions) pada pengujian fungsional sistem HYDE

A. BLACK-BOX TESTING (PLAYWRIGHT)

Modul: auth.spec.ts (Login & Routing)

  1. Valid student login navigates away from /login, not to /admin
  2. Valid admin login redirects to /admin area
  3. Wrong password shows generic error, no standalone "password salah"
  4. Wrong NIM same generic error format as wrong password
  5. Empty form blocked by HTML required, does not call API
  6. Unauthenticated visit to /admin redirected to /login
  7. Unauthenticated visit to /student redirected to /login
  8. Student visiting /admin after login redirected away from /admin
  9. Admin visiting /student after login middleware does not redirect from /student root
  10. After login, refreshing the page still logged in (session persists)

Modul: hybrid.spec.ts (Alur QR & Fisik)

  1. Admin advances HYBRID transaction (REVIEWING → AWAITING_SCAN)
  2. Admin generates disposisi on VALIDATED HYBRID status moves to AWAITING_SCAN
  3. /admin/scan page loads with camera UI for admin
  4. /admin/scan as student redirected away
  5. Mock scan via API status becomes VALIDATED with scannedAt set
  6. COMPLETED HYBRID on /v/[id] shows physical verification heading

Modul: security.spec.ts (Privasi & Limitasi)

  1. /v/[id] public page does NOT contain student NIM in HTML
  2. /v/[id] does NOT expose fileUrl or message contents
  3. Direct blob URL access without auth blocked
  4. Student A cannot access Student B's files via /api/blob/proxy
  5. Rate limiting: 6 rapid login attempts 6th returns 429 (Too Many Requests)
  6. GET /api/transactions without auth protected (401 or redirect to /login)
  7. Student calling /api/transactions/[id]/scan returns 403 (role guard)
  8. Admin from different transaction calling scan returns 403 (ownership guard)

Modul: transaction.spec.ts (Alur Digital Penuh)

  1. Student creates DIGITAL transaction status is DRAFT
  2. Student creates HYBRID transaction status is DRAFT
  3. Student A cannot see Student B's transaction (403)
  4. Admin can see their assigned transaction
  5. Admin claims transaction (DRAFT → REVIEWING)
  6. Admin sends to REVISION student sees REVISION status
  7. Student resubmits from REVISION status moves back to REVIEWING
  8. Admin approves DIGITAL transaction (REVIEWING → VALIDATED)
  9. DIGITAL VALIDATED transaction shows complete for student

B. WHITE-BOX TESTING (JEST)

Modul: auth.test.ts (Logic Session & Role)

  1. Returns session when valid session and DB user exist (no role required)
  2. Throws UNAUTHORIZED when no session exists
  3. Throws FORBIDDEN when DB role does not match required role
  4. Throws UNAUTHORIZED when user no longer exists in DB (deleted user)
  5. Uses DB role for verification - not the JWT role

Modul: blob-proxy.test.ts (File Access Logic)

  1. Missing url param returns 400
  2. File record not found in DB returns 404
  3. Stranger (not student or admin) requests file returns 403
  4. Transaction student (owner) can access their file returns 200 proxied response
  5. Assigned admin can access the file returns 200 proxied response

Modul: ownership.test.ts (Akses Data Internal)

  1. Student reads their own transaction returns 200
  2. Student reads another student's transaction returns 403
  3. Assigned admin reads their transaction returns 200
  4. Unassigned admin reads a transaction returns 403
  5. Student calls scan endpoint returns 403
  6. Non-assigned admin calls scan returns 403 (ownership guard)

Modul: qr-parser.test.ts (Generate/Decode URL)

  1. Valid URL with correct domain and /v/[id] path returns id
  2. Wrong domain URL returns null
  3. URL missing /v/ path segment returns null
  4. Completely invalid string (not a URL) returns null
  5. Empty string returns null

Modul: scan.test.ts (Logic Pemindaian QR)

  1. Returns 400 if transaction mode is DIGITAL (not HYBRID)
  2. Returns 400 if transaction status is not AWAITING_SCAN
  3. Returns 403 if adminId does not match session user id
  4. Returns 404 if transaction does not exist
  5. On success: status = VALIDATED, scannedAt and completedAt are set
  6. On success: StatusLog entry written with AWAITING_SCAN → VALIDATED
  7. On success: response includes student name and destinationName

Modul: status-transitions.test.ts (State-Machine)

  1. DIGITAL: REVIEWING → VALIDATED is allowed
  2. DIGITAL: REVIEWING → AWAITING_SCAN is NOT allowed
  3. DIGITAL: AWAITING_SCAN → VALIDATED is NOT allowed (no such DIGITAL state)
  4. HYBRID: REVIEWING → AWAITING_SCAN is allowed
  5. HYBRID: AWAITING_SCAN → VALIDATED is allowed
  6. HYBRID: REVIEWING → VALIDATED returns false (must go via AWAITING_SCAN)
  7. Any mode: VALIDATED → anything returns false (terminal state)
  8. Student attempting REVIEWING → VALIDATED for own DIGITAL tx returns 403 (STUDENT can only move REVISION REVIEWING)
  9. Admin: DIGITAL REVIEWING → VALIDATED succeeds and sets completedAt
  10. Admin: DIGITAL VALIDATED → anything returns 400 (terminal state)
  11. Admin: HYBRID REVIEWING → AWAITING_SCAN succeeds
  12. Admin: HYBRID REVIEWING → VALIDATED returns 400 (must go via AWAITING_SCAN)
  13. HYBRID AWAITING_SCAN → VALIDATED sets completedAt (and scannedAt)
